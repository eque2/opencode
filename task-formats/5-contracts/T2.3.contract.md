# Contract T2.3 — Update the router so a pair configured to serve nothing is not treated as unconfigured

> **Goal.** Make a deliberately-emptied pair fail loudly instead of silently reverting to the built-in default.

## Requires

- T1.3 is trusted — Implement the rows → policy-document projection
- T1.6 is trusted — Add the serve-nothing set to the policy document and its identity

## Changes

- `libs/media/src/provider-router.ts` — update: a pair configured with zero enabled providers fails with a new typed error instead of falling through to default precedence

## Ensures

What must be true when the work is done.

- **T2.3.c1** — a configured pair routes to its first enabled candidate in stored order, reported as `'policy'`.
  - proof: the test tagged `[T2.3.c1]`
  - judge: runner + verifier
  - category: happy path
- **T2.3.c2** — an absent pair routes by `orderedCandidatesFor`, reported as `'default-precedence'`.
  - proof: the test tagged `[T2.3.c2]`
  - judge: runner + verifier
  - category: empty / null; relates to S6, S44
- **T2.3.c3** — a pair configured with every provider disabled fails with a typed error naming the pair, distinguishable from the absent case.
  - proof: the test tagged `[T2.3.c3]`
  - judge: runner + verifier
  - category: boundary; relates to S7
- **T2.3.c4** — a disabled provider is never a candidate, even when every enabled candidate has failed.
  - proof: the test tagged `[T2.3.c4]`
  - judge: runner + verifier
  - category: boundary; relates to S3, S22
- **T2.3.c5** — an override naming a disabled provider is refused by the existing `OverrideNotACandidate`, not silently honoured.
  - proof: the test tagged `[T2.3.c5]`
  - judge: runner + verifier
  - category: invalid input
- **T2.3.c6** — candidate order is verbatim and never re-sorted; a policy for a pair remains strictly additive over default precedence for every pair that is merely absent.
  - proof: the test tagged `[T2.3.c6]`
  - judge: runner + verifier
  - category: regression

## Rejected proofs

A verdict that accepts one of these is void.

- c3: asserting only that an error occurred. Assert the error's tag and the pair it names; only that separates serve-nothing from absent.
- c4: a single failing candidate. Fail every enabled candidate, then assert the disabled provider was never called.

## Approach

Guidance for the builder. Not an obligation; nothing here is judged.

This is the one genuine semantic change to `provider-router.ts`. Today an absent entry and a serve-nothing entry are indistinguishable; after this they must not be. Add a tagged failure alongside the existing `NoCandidateSatisfiesConstraints` rather than reusing it — the operator response differs completely ("your constraints excluded everything" versus "you switched everything off").
