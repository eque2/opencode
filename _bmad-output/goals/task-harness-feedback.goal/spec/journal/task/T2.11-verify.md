## Observation (not a verdict ground)

The lease release is keyed by run id only, and the run id is fixed per spec (`TaskEvents.runID(directory,
specPath)`). After an early release (UI24), a new `/task` of the same spec could claim, and the old job's finalizer
release would free that new claim. The claim token on BackgroundJob.start closes most of this window; a narrow
interleaving remains. Worth a look when the finalizer-order test is written.

## What would earn trust

- Test `/task` with empty arguments: the usage line, no claim, no start.
- Test a live run plus a dirty (or detached) checkout: the busy line, not a git refusal.
- Test a resumed slice whose `run.started` base differs from the checked-out branch: the refusal, no claim, no start.
- Test the job finalizer order: the lease is still held while the cancel finalizer records `run.cancelled` (and
  after the writer's last write), and is free only after.
- Test `/task` over a stored slice whose fold dies: the reply carries the new-run note.
- Optionally: a command/job test that resumes a stored slice and stores `run.resumed` with the normalised path; a
  no-file assertion in the two-call concurrency test.
