## Test case by test case

1. **Happy Path (SV8) — none / claimed / busy { runID, spec, path } / release.** Test 1 asserts `live` = none,
   `claim` = claimed, `live` = Some(lease), second claim `toEqual` busy, release frees, re-claim claimed.
   **GAP:** both claims use the same `spec` and `path`, and `spec === path`
   (`"task-formats/blend/release-notes.spec"` for both fields of both claims). So the busy assertion proves only that
   `runID` is the live run's. A busy answer that echoes the requester's `spec`/`path`, or a `live`/busy mapping that
   swaps `spec` and `path`, passes unchanged. SV8 requires the line to name "the live run's spec and path".
   Fix: give the second claim a different spec and path, and make `spec !== path` in each claim.
2. **Error Propagation — a failed start is released in the same onExit; claim, fail, claim again.** Test 2 runs
   `withClaim` with `start = Effect.fail(...)`, asserts the exit is a failure, `live` = none, and the next claim is
   claimed. This kills the "no release on failure" mutation. **GAP:** the test never observes the claim as held (no
   `live` = Some inside `start`), so it also passes for a `withClaim` that never claims. No test shows that a
   successful start keeps the lease, so a `withClaim` that releases on every exit (success included) passes all 7
   tests; that mutant lets a second `/task` start beside a live run. Fix: assert inside `start` that `live` returns
   the claiming run, and add a success case that leaves the lease held (busy for the next claim).
3. **Happy Path (SV13) — session.claim adds an entry, the claimer waits, removing the run drops its entries.**
   Test 5: three claims (task:, scenario: of `task_a`, task: of `task_z`); `ownerOf` returns the entry right after
   `claimSession` returns; unknown session = none; a re-claim replaces the entry; `removeRun("task_a")` drops both
   `task_a` entries and keeps the `task_z` entry. Covered.
4. **Security Boundaries — trust reaches only that directory's supervisor; outside vs external record rule.** Test 7:
   two directories, two stub supervisors; `trust(one, "T9")` gives `["T9"]` to `run:task_one` and `[]` to
   `run:task_two`; a trust for a directory with no live run does not fail. Covered for the forwarding half. The
   record rule (outside only, never external) is deferred by the task's own SV20 case to T2.10, whose Security
   Boundaries case covers it. Accepted.
5. **Boundary — running ⇔ system.get("run:<runID>") is Some; system id formats.** Test 6: `running` false, spawn,
   true, remove, false; `systemId.task` and `systemId.scenario` formats asserted; test 7 reads `run:<runID>` through
   `harness.system.get` directly. Covered.
6. **Concurrency — lease holds checkout and git Semaphores; two merges serialise.** Test 4: two concurrent
   `checkout.withPermit` sections run in order `one start, one end, two start, two end`. Covered for the checkout
   lock. Weak (not a rejection reason alone): the git lock is only checked as `not.toBe(checkout)`, which does not
   prove it is a one-permit lock.
7. **Timing — N/A.**
8. **Happy Path (SV20) — forward `/task trust T9` to `run:<runID>` of the directory (stub actor).** Test 7. Covered.
9. **Invalid Input — `/repo`, `/repo/`, symlink are one lease; release by a non-holder changes nothing.** Test 3 uses
   a real temp directory and a real symlink; the second and third claims are busy. Test 1: release by `task_b` leaves
   `live` Some. Covered. Weak: the non-holder check asserts only `isSome`, not that the lease is still `task_a`'s.
